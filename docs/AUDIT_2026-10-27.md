## 2. Anomalies trouvées et corrigées

### 2.1 Le lien de désinscription était inutilisable — **corrigé**

Le lien inséré dans les messages d'information pointait vers
`/espace-membre/profil?desinscription=<id>`, page réservée aux membres approuvés
**connectés**. Une personne qui reçoit un e-mail ne pouvait donc pas s'en servir :
le seul moyen de se désinscrire exigeait de se connecter.

Correction : désinscription par **jeton signé**, indépendante de la session.

- `backend/src/services/email/unsubscribe.ts` : jeton `base64url(<profil>:<expiration>)`
  + `HMAC-SHA256` avec `SESSION_SECRET`, comparaison à temps constant, validité
  180 jours, identifiant contrôlé au format UUID avant tout accès à la base.
- `GET /api/v1/public/unsubscribe?token=…` : vérifie le lien, renvoie l'adresse
  **partiellement masquée**, ne modifie rien.
- `POST /api/v1/public/unsubscribe` : applique la désinscription (`email_opt_out`),
  idempotente, limitée à 20 appels/heure/IP, journalisée dans l'audit
  (`email.unsubscribe`).
- Page publique `/desinscription?token=…` : confirmation explicite, donc un lien
  ouvert automatiquement par un antivirus ou un filtre antispam ne désinscrit
  personne.
- L'aperçu de campagne utilise désormais le profil de l'administrateur : le lien
  affiché est un vrai lien, testable (il pointait auparavant vers un identifiant
  factice `apercu`).

Vérifié de bout en bout : envoi d'une campagne → extraction du lien dans le HTML
reçu → `GET` (200, adresse masquée) → `POST` (200, `changed: true`) → l'intéressé
n'est plus destinataire d'une campagne ultérieure (`recipients` 4 → 3,
`excluded: 1`), la préférence est visible en base, l'action est dans le journal
d'audit, et un second clic ne change plus rien.

### 2.2 `LOG_LEVEL` documenté mais sans effet — **corrigé**

README, `DEPLOIEMENT.md` et `.env.example` présentaient `LOG_LEVEL` comme un
réglage actif, alors que le code écrivait directement sur `console`. Le réglage est
maintenant implémenté (`backend/src/utils/logger.ts`) et utilisé par tous les
journaux du serveur : seuil respecté, horodatage ISO, niveau affiché, pile des
`Error` conservée. En environnement de test, seules les erreurs sortent pour
garder une sortie lisible. Les scripts en ligne de commande continuent d'écrire
directement sur la console : leur but est de parler à l'opérateur.

Vérifié : avec `LOG_LEVEL=warn`, les lignes de démarrage disparaissent ; avec
`LOG_LEVEL=debug`, elles réapparaissent.

### 2.3 `SUPABASE_JWT_SECRET` déclaré mais jamais lu — **corrigé**

Variable validée dans le schéma d'environnement et documentée, mais lue nulle part :
la vérification des jetons Supabase passe par le client `anon`
(`supabaseProvider`). Le réglage a été retiré du schéma, de `.env.example` et du
README, plutôt que de laisser croire qu'il est nécessaire.

### 2.4 `npm run db:seed -- --force` ne transmettait pas `--force` — **corrigé**

Les scripts de la racine s'arrêtaient au premier `npm run … --workspace`, qui
absorbait l'argument : `--force` n'arrivait jamais au script, et le seed refusait
de s'exécuter sans que l'on comprenne pourquoi. Les scripts racine se terminent
désormais par `--`, ce qui transmet les arguments (`db:seed`, `db:migrate`,
`db:reset`, `create-admin`). Vérifié : `npm run db:seed -- --force` réinjecte
effectivement le jeu de démonstration. `npm run init-super-admin` a aussi été
ajouté à la racine (il manquait, alors que la documentation le citait).

### 2.5 Documentation périmée — **corrigée**

- README et `docs/ROLES_ET_PERMISSIONS.md` montraient
  `npm run create-admin -- <email> <mot-de-passe>`. Le script **refuse** désormais
  un mot de passe en argument (il resterait dans l'historique du shell) : la
  commande affichée était donc inopérante. Remplacée par
  `npm run init-super-admin -- --email <adresse>`, avec saisie masquée.
- README : le tableau des migrations ne citait que `0001`–`0003` ; les sept
  migrations sont maintenant décrites.
- README : `init-super-admin` ajouté à l'arborescence des scripts et à la table des
  commandes ; l'endpoint `unsubscribe` ajouté au tableau de l'API.
- `docs/DEPLOIEMENT.md` : procédure du premier administrateur alignée sur la
  saisie masquée.
- `docs/MESSAGERIE.md` : la désinscription est décrite telle qu'elle fonctionne
  (jeton signé, sans connexion, confirmation, endpoints).
- `all_members` mentionné comme alias historique de l'audience `approved`
  (accepté pour ne pas casser les intégrations, non proposé dans l'interface).

## 3. Points restant à la charge de l'exploitant

1. **Création du compte principal** : le mécanisme est livré et testé
   (`npm run init-super-admin -- --email <adresse>`), mais le compte
   `joannegnava@gmail.com` **n'existe pas encore** sur la base Supabase distante.
   La commande doit être lancée depuis un environnement disposant de
   `DATABASE_URL` ; le mot de passe est saisi à l'invite masquée et n'est jamais
   transmis à un tiers.
2. **Migrations distantes** : les sept migrations sont déjà appliquées sur le
   projet Supabase dédié ; la base ne contient aucun profil.
3. **Envoi réel des e-mails** : `MAIL_DRIVER=smtp` (et un SMTP configuré) reste
   nécessaire en production ; en `log`, les messages vont au journal.
